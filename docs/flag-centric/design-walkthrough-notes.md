# Design walkthrough notes — flag-centric solution design (P2 review, rev 3)

Date: 2026-10-04. Author: solution-architect (Maker). Applies to `docs/flag-centric/solution-design.md` rev 3 (rev 3 adds round-2 findings TM-IMP, L-ORDER, the audit-cap decision and the grant-lifetime check).
Sources: SR = security-reviewer, TM = threat-modeler, ORCH = orchestrator verification.
Rule: "fixed in doc §x" is used only where the doc text was changed. Every claim below was checked against `feature_flag/src/main/java/org/aibles/feature_flag/` (BE/) before acceptance.

## Verification of reviewer claims

| Claim | Verdict | Evidence |
|---|---|---|
| updateState never asserts env.project == flag.project | Confirmed | BE `service/impl/FeatureFlagServiceImpl.java:217-223` loads env by id and calls `check` with the flag's projectId plus the foreign env. `getState` (`:198-209`) has no assertion either. |
| ...and it is exploitable as a write IDOR today | Partially. Not confirmed as a write path | Every state-creation path uses an env from the flag's own project (`FeatureFlagServiceImpl.java:76-82`, `EnvironmentTransferServiceImpl.java:76-85,246-266`), so the pair lookup at `:225-229` returns 404 for a foreign env. Today's impact is an information oracle: PROD elevation and change window are evaluated on the foreign env's attributes, so you get 403 or 404 depending on its type. It becomes a write IDOR if lazy-create is added. This is still a pre-existing backend defect. |
| Toggle wipes value | Confirmed by reading the code. Not tested against the DB | `FeatureFlagServiceImpl.java:236` is unconditional. `:237` null-guards rollout. The nulled value then reaches audit (`:240-246`), webhooks (`webhook/WebhookDispatcher.java:59-60`) and Slack (`notification/SlackEventListener.java:31-37`). |
| FlagEnvironmentState has no @Version | Confirmed | Grepping BE/ for `@Version` finds nothing. `GlobalExceptionHandler.java:33-41` maps 409 only for `DuplicateResourceException`. There is no optimistic-lock handler (it falls to the catch-all at `:125`). |
| No value validation | Confirmed | `dto/request/UpdateFlagStateRequest.java:9` has no constraints. Nothing in updateState parses `value` by `valueType`. |
| Clock uses system default zone | Confirmed | `config/AppConfig.java:12`; `PermissionService.java:226`. No TZ setting in `application.properties` or the `Dockerfile` (grep). The runtime zone is unverified. |
| Page size cap | Code clamps to 100, not 200 | `config/PaginationConfig.java:22,27`. The doc uses 100, the stricter of the two. |
| Admin API has no rate limit | Confirmed | Only the auth and SDK filters exist (`security/ratelimit/*`, `application.properties:26-31`). |
| Import is a second state-write path that skips F19, version and per-flag audit (TM, round 2) | Confirmed | `EnvironmentTransferServiceImpl.java:237-241` overwrites `value` with no size/type check (`ImportEnvironmentRequest.java:67` has no constraint; only the declared `valueType` is compared, `:207-215`) and no version check. `:217-226` creates a state for an existing flag that lacks one at the target, whatever the strategy. `:169-178` writes one `ENVIRONMENT`/`IMPORT` row whose `after` is the counts only (`ImportResultResponse.java:25-30`). No `publishEvent` in this class, so no webhook/Slack. Authorization does apply PROD/change-window rules to the target env (`:141-146`). |
| Env check before access control leaks 404 vs 403 (TM, round 2) | Confirmed against rev 2 text | Rev 2 §6.3 item 1 put the env-in-project assertion before any `check`, so a caller with no access to the flag's project would get 404 for a foreign env and 403 for an env of that project. |
| Reads are not audited | Confirmed | `AuditService.java:22-26`. Only mutations are recorded. |
| CONFLICT: SR says AUDIT_READ is org-scope only, so a user with only a project grant cannot see history. TM says VIEWER can read audit. | Both are right about the mechanism. SR's scenario cannot happen in the current data model. | `AUDIT_READ` is in VIEWER (`PermissionService.java:69-70`), so TM is right. `AuditService.list` checks at org scope (`AuditService.java:72`) and ignores project grants (`PermissionService.java:143-145,230`), so SR's mechanism is right. A grant requires org membership (`ProjectGrantServiceImpl.java:89-92`) and member role is NOT NULL (`OrganizationMember.java:34-35`), so every grantee is at least an org VIEWER and can read the **whole org** audit. The real issue is that audit read is too broad, not that history is invisible. A grant cannot outlive membership through member removal: `OrganizationServiceImpl.removeMember` deletes the member and then all of that user's project grants in the org's projects in the same `@Transactional` method (`:157`, `:170`, `:174-180`), and it is the only member-delete call in the service layer (grep `memberRepository.delete`: only `:170`). Residual: grant revocation has no audit entry of its own, and DB-level cascades were not reviewed. Whether audit should be project-scoped is policy, so it goes to Security as Q7. |
